# ADR 0001: 도메인별 확대 구조로 보고서를 제공

Date: 2026-09-19

## Status

Accepted (2026-10-10)

## Purpose

사용자는 짧은 기술 설명까지 보고서로 생성돼 파일과 브라우저를 불필요하게 여는 문제를 줄이려 한다. 짧고 단순한 답은 대화 안에서 전달하고, 여러 조건·관계·근거를 함께 따라가야 해 보고서가 이해를 실질적으로 돕는 내용은 자동으로 보고서를 제공한다. 어느 쪽이 적절한지 애매하면 사용자에게 전달 방식을 확인한다. 생성하기로 한 리뷰·평가·분석 리포트는 출력 형식이나 진입 경로가 달라도 같은 읽기 원칙으로 핵심 판단과 다음 행동을 설명해야 한다.

사용자는 모든 리포트에 공통 작성 스킬을 적용하고, 같은 대상을 전체 의미에서 내부 구조와 구체적인 동작으로 확대하는 계층을 요구했다. 상위에서는 세부사항을 감추고 사용자에게 익숙한 비유로 접근할 수 있게 하며, 하위에서는 그 비유를 실제 책임·규칙·예외와 연결해 정확히 이해할 수 있어야 한다. 이미 알려진 사용자 배경은 비유와 설명의 출발점을 정하는 데 활용한다. 같은 수준의 세부 항목이 다섯 개 이상이면 내용을 버리지 않고 설명 범위를 다시 나눠야 한다.

사용자는 설명할 관계를 근거와 전달 형식 안에서 표현할 수 있으면 그림을 기본으로 제공하기를 원한다. 그림은 이해를 돕는 수단이며, 그림 부재 자체가 보고서의 완료를 막는 필수 조건은 아니다.

여러 작업을 병행하는 사용자는 보고서만 다시 열어도 어떤 요청으로 작성됐고 당시 무엇을 확인하려 했는지 알 수 있어야 한다. 제목 아래에서 요청한 작업과 대상, 확인된 배경과 의도를 짧게 복원한 뒤 결론으로 이어져야 대화를 다시 찾아가는 부담을 줄일 수 있다. 도입부에는 눈에 보이는 제목이 필요하지만, 다양한 보고서의 본문을 같은 절 이름과 구성으로 제한해서는 안 된다.

보고서 작성은 리뷰·평가를 담당하는 adr-writer의 기능이다. 두 플러그인을 함께 설치해도 같은 보고서 스킬과 세션 지침이 중복 노출되지 않아야 한다.

독자가 보고서를 읽은 뒤 핵심 내용의 의미와 적용 조건을 스스로 확인할 수 있어야 한다. 문서의 핵심 내용을 다루는 중간 난이도 퀴즈 생성은 강하게 권고하지만 필수 산출물은 아니다. 퀴즈의 목적은 이해도를 높이고 인지부하, 즉 내용을 이해하는 동안 한꺼번에 기억하고 연결해야 하는 부담을 줄이는 것이다.

## Decision Drivers

- 짧고 단순한 요청은 대화로 충분히 이해할 수 있어야 하며, 복잡한 요청은 보고서의 단계별 설명으로 이해를 도와야 한다. 전달 필요성이 애매할 때만 확인하고, 생성한 보고서는 요청 맥락과 전체 판단에서 필요한 도메인과 근거로 이어져야 한다.
- 가독성을 높이는 과정에서 사실·조건·검증 결과를 잃거나 존재하지 않는 시스템 경계를 만들어서는 안 된다. 그림을 제공하기 어려운 조건에서도 정확한 설명을 전달할 수 있어야 한다.
- 직접 요청, 내부 리뷰, 자동 생성과 출력 형식이 달라도 작성·검증 기준이 일관돼야 하며, 두 플러그인을 함께 설치해도 보고서 기능의 안내는 한 번만 제공해야 한다.
- 이해도 확인은 핵심 개념에 집중하고 문제 수와 정보 공개 순서를 제한해야 한다. 사소한 암기 문제나 정답의 조기 노출은 이 목적에 맞지 않는다.

## Decision

보고서 작성 스킬 `report-writer`는 adr-writer만 제공하며, alps-writer에는 보고서 스킬이나 이를 요구하는 세션·작성 지침을 포함하지 않는다. 보고서 생성 여부는 사용자의 명시적 요청과 이해에 필요한 복잡도로 먼저 정한다. 생성하기로 한 adr-writer의 사람용 리포트는 공통 보고서 작성 기능을 거치며, 다른 형식이나 전달 제한을 요청하지 않으면 독립 HTML 파일로 생성해 검증한 뒤 운영체제의 기본 브라우저에서 한 번 연다. 리포트는 제목 아래의 `배경과 목표`에서 짧은 요청·배경 설명을 시작하고, 결론과 중요한 한계, 도메인별 상세 근거 순서로 읽힌다. 도입부 제목은 고정하되 이후 절의 제목과 구성은 독자의 질문과 보고서 주제에 맞게 정한다. 확인한 도메인·서브도메인·바운디드 컨텍스트와 그 안의 업무 책임을 따라 설명을 확대한다.

C4의 확대 아이디어를 읽기 구조로 사용하되 모든 리포트에 특정 C4 다이어그램이나 기술 계층을 강제하지 않는다. DDD의 도메인 경계는 보고서의 주제와 책임을 묶는 근거로 사용한다. 보기 좋게 나누기 위해 실제 시스템에 없는 바운디드 컨텍스트를 채택한 것처럼 서술하지 않는다.

근거와 전달 형식으로 표현할 수 있는 관계는 각 설명 수준에서 그림으로 제공하는 것을 기본으로 한다. 전체 시스템이나 여러 단계의 과정은 짧은 배경과 답 뒤의 개요 그림에서 시작해 같은 책임의 내부 관계로 확대한다. 그림은 필수 산출물이 아니며, 제공할 수 없거나 사용자가 제외한 경우에는 설명과 근거로 전달한다.

설명의 깊이는 같은 대상의 추상화 수준으로 정한다. 상위에서 익숙한 비유로 전체 역할을 이해한 독자가 하위에서 그 역할을 실현하는 구조와 동작을 설명할 수 있어야 한다. 펼침 조작, 같은 수준의 다른 사례로 이동하기, 원본 근거 열기만으로는 추상화 수준이 내려간 것으로 보지 않는다. 비유는 실제 대상과의 대응 관계 및 적용 한계가 분명해야 하며, 정확한 계약을 대신하지 않는다.

보고서는 에이전트가 자율적으로 정한 중요한 선택이 사용자의 원래 의도에 부합하는지
판단할 수 있게 설명한다. 모든 세부사항을 요구사항으로 열거할 수 없으므로, 사용자의 문제,
원하는 결과와 확인된 범위·우선순위가 그 선택의 기준이 된다. 관련 의도, 선택과 근거, 관찰한
결과를 연결하고, 테스트 통과나 일반적인 관례만으로 목적 달성을 주장하지 않는다.

의도는 계약과 승인 범위 안의 판단을 안내한다. 보고서는 허용된 구현 재량과 새 정책·범위
변경을 구분하고, 중요한 선택이 모호한 경우 필요한 질문과 독립적으로 진행할 수 있는 작업을
설명한다. 첫머리의 요청 맥락을 제공한 뒤 상세 설명에서는 고정된 프레임워크보다 그 판단 문맥이 보존되었는지를 검토하며, 실제로
확인한 결과와 기대하는 효과를 구분한다.

공통 보고서 작성 기능은 핵심 내용에 대한 이해도 퀴즈의 생성·배치·자가 확인을 담당한다. 구현 리뷰를 포함한 개별 보고서 기능은 이 공통 규칙을 사용하며, 자신의 검토 범위·판정·승인 규칙을 유지한다.

```mermaid
flowchart TD
    R["요청 맥락: 작업·배경·의도"] --> A["개요: 핵심 답변과 한계"]
    A --> B["익숙한 설명으로 전체 역할 이해"]
    B --> C["같은 대상의 책임과 내부 관계"]
    C --> D["규칙·예외·구체적인 동작"]
    E["각 설명을 뒷받침하는 원본 근거"] -.-> A
    E -.-> C
    E -.-> D
```

### Requirement contract

#### 1. 적용 범위와 의미 보존

##### 적용 범위

- 사용자가 보고서 작성·수정을 명시적으로 요청하거나 보고서 스킬을 직접 호출하면 복잡도와 무관하게 공통 작성 스킬을 적용한다. 사용자가 정한 형식·파일 생성·열기 제한은 그 범위에서 우선한다.
- 일반 기술 설명·리뷰·분석은 독자가 답을 이해하기 위해 연결해야 하는 조건·관계·비교·근거를 기준으로 판단한다. 단계별 설명, 시각화나 근거 탐색이 이해를 실질적으로 돕는 복잡한 내용은 별도 확인 없이 보고서를 생성한다. 기술 주제, 리뷰라는 요청 이름, 글자 수나 항목 수만으로 생성하지 않는다.
- 짧은 설명이나 작은 목록으로 필요한 답과 근거를 충분히 전달할 수 있는 단순한 내용은 대화로 답하며, 별도 보고서 파일·브라우저 열기·퀴즈를 추가하지 않는다. 간단한 용어 설명, 한 단계 조작 안내와 국소적인 리뷰 결과도 이 기준으로 판단한다.
- 보고서가 이해를 실질적으로 도울지 애매하면 생성 전에 한 번 짧게 물어본다. 같은 범위에서 이미 정한 전달 방식은 다시 묻지 않으며, 답변을 기다리는 동안 보고서 생성 여부와 독립적인 조사·작업은 계속한다. 응답이 없다는 이유로 파일 생성에 동의한 것으로 취급하지 않는다.
- 이미 사용자가 선택한 전문 워크플로가 명시적으로 요구하는 보고서·감사 산출물은 유지한다. 단순히 리뷰·평가·동기화라는 작업 종류에 속한다는 이유로 필수 산출물이 있다고 추정하지 않는다. 보고서를 생성하기로 한 뒤에는 HTML, Markdown, 텍스트와 다른 형식에 같은 의미·구조·품질 원칙을 적용한다.
- 자동 생성 리포트도 같은 구조와 검증 계약을 따른다. 사용자 동의 없이 추가 유료 모델 호출을 도입하지 않으며, 수행하지 않은 의미 검토나 시각 검증을 완료했다고 주장하지 않는다.
- 기계용 원본 데이터와 PRD·ADR의 기존 필수 스키마는 보존한다. 사람용 리포트 보기와 설명을 재구성하되 요구사항, 정확한 값·단위, 허용 상태·권한·순서, 실패 보장, 검증 결과와 원본 근거를 누락하지 않는다.
- 단순 인사·질문·진행 알림을 긴 보고서로 만들지 않는다. adr-writer 단독 설치 상태에서 보고서 요청에 공통 기능을 자동으로 선택할 수 있어야 한다. 두 플러그인을 함께 설치했을 때 보고서 스킬과 세션 시작·복원 시의 보고서 지침은 각각 한 번만 제공한다.

##### 생성 여부의 관찰 가능한 검증 기준

- 짧은 용어 설명이나 국소적 리뷰 결과는 별도 보고서 요청이 없을 때 파일 생성·브라우저 열기 없이 필요한 답과 근거를 전달한다.
- 여러 구성 요소의 실패 흐름이나 조건이 얽힌 대안 비교처럼 단계별 설명이 필요한 요청은 별도 생성 승인을 묻지 않고 보고서를 제공한다.
- 보고서의 유용성이 애매한 요청은 전달 방식만 한 번 확인하며, 답변 전에는 보고서 파일을 생성하지 않는다. 같은 범위의 기존 답변은 재사용한다.
- 짧은 주제라도 사용자가 보고서를 명시적으로 요청하면 생성하며, 파일 금지·다른 형식·열기 금지 요청과 전문 워크플로의 필수 원본 산출물을 보존한다.

##### 펼친 문서와 인쇄

- HTML은 모든 깊이의 하위 설명을 기본으로 펼쳐 처음부터 순서대로 읽고 배포할 수 있게 한다. 상세 근거·로그·코드 원문은 기본으로 접되, 결론·한계·필요한 행동을 이해하는 데 필요한 근거는 본문에 설명하거나 해당 근거를 펼쳐 제공한다. 근거가 필수 목록에 포함됐다는 이유만으로 모두 펼치지는 않으며 원본 접근과 계약·판정은 보존한다.
- 사용자가 접힌 화면을 명시적으로 요청한 경우에는 그 선택을 따르며, 독자가 화면에서 직접 접을 수 있는 조작은 유지한다. 인쇄 시에는 화면의 접힘 여부와 관계없이 본문·그림과 필요하다고 표시한 근거를 포함하고, 선택적 근거는 독자가 펼쳐 둔 범위만 포함한다. 인쇄가 끝나면 독자가 선택했던 화면 상태를 복원한다.
- 인쇄물은 제목·설명·그림이 읽기 순서대로 이어지고 긴 본문이나 근거가 잘리지 않아야 한다. 좁은 페이지에서 과도한 중첩 여백과 스크롤 영역을 제거하고, 제목만 떨어지거나 그림의 글자가 읽기 어려워지는 구성을 피한다. Mermaid 원문은 보조 자료로 접근 가능하게 보존하되 기본 인쇄에서는 제외하며, 퀴즈의 네 선택지는 인쇄하고 정답·피드백·선택 표시·조작 버튼은 제외한다.

##### 기본 전달

- 적용 범위 판단에서 생성하기로 한 보고서는 별도 형식을 요청하지 않으면 독립 HTML 파일로 작성한다. 기존 작업이 요구하는 Markdown·JSON 원본은 유지한다. 대화로 전달하기로 한 간단한 결과에는 HTML 기본값을 적용하지 않는다. 명시적인 다른 형식, 채팅 전용, 파일 생성 금지, 열기 금지나 특정 브라우저 요청은 그 범위에서 우선한다. 단순 완료 안내는 별도의 보고서가 아니다.
- 의미·구조·근거와 파일 존재·비어 있지 않음을 확인한 뒤 최종 HTML을 운영체제의 기본 브라우저에서 한 번 연다. 초안 작성 중이나 렌더러를 호출할 때마다 자동으로 열지 않는다. 특정 브라우저 요청이 없으면 작업 전용 자동화 브라우저나 로컬 서버를 전달 수단으로 추가하지 않는다.
- 브라우저를 열 수 없거나 열기가 실패해도 생성한 보고서를 보존하고 절대 경로와 실제 실패 원인을 전달한다. 열기 성공과 화면의 시각 검증은 구분하며, 브라우저 자동화 검증은 사용자가 요청한 경우에만 수행한다.

#### 2. 도메인 계층과 항목 상한

##### 첫머리의 요청 맥락과 결론

- 제목 바로 아래에는 독립된 `배경과 목표` 제목을 표시한다. 영어 보고서는 `Background and goals`를 사용한다. 그 아래에 요청한 작업과 대상, 요청 계기와 원하는 결과를 짧게 정리한다. 작업을 구분하는 데 필요한 범위·비교 대상·우선순위도 확인된 경우 포함한다. 관찰 기준은 대화 기록을 열지 않고 보고서의 첫머리만 읽어 어떤 작업이며 왜 요청됐는지 구분할 수 있는 것이다.
- 요청 맥락은 대화와 제공 자료에서 확인한 내용만 사용한다. 의도나 배경을 추측해 사실로 쓰지 않으며, 없는 정보로 빈 항목을 채우거나 대화·작업 이력을 길게 복사하지 않는다. 관찰 기준은 요청 설명의 각 사실을 제공된 맥락으로 뒷받침할 수 있는 것이다.
- 요청 맥락 바로 다음에 독자의 질문에 대한 답, 중요한 영향·제약과 다음 행동을 전달한다. 배경·목표와 답은 표시 영역을 구분하며, 답에 별도 제목이 필요하면 보고서 주제에 맞게 선택한다. 이후 관련 도메인을 선택해 책임·상호작용·구현과 근거로 내려간다. 관찰 기준은 요청 설명과 결론 사이에 목차·상세 근거·과정 설명이 끼어들지 않는 것이다. 배경이 분리되지 않은 기존 입력은 내용을 보존해 읽을 수 있게 하며 배경을 추측하거나 결론을 배경으로 재분류하지 않는다.
- 이후 절은 보고서 주제와 독자가 확인할 질문에 맞게 이름과 구성을 정하며, 공통 절 목록이나 빈 항목을 강제하지 않는다. 읽기 순서, 도메인별 계층, 필수 근거와 개별 검토의 판정·필수 항목은 보존한다. 관찰 기준은 서로 다른 종류의 보고서가 각 주제에 맞는 제목을 사용하면서 이 공통 원칙을 만족하는 것이다.

##### 도메인별 상세와 근거

- 계층의 묶음은 확인한 서브도메인·바운디드 컨텍스트를 우선 사용하고, 내부에서는 그 컨텍스트의 업무 책임과 개념으로 세분한다. 기술 계층, 파일 순서, 작업 순서나 임의의 번호 구간을 도메인 경계로 대신하지 않는다.
- 한 노드의 직접 하위 설명 단위는 최대 4개다. 하위 절, 독립 목록·카드와 비교 항목이 5개 이상이면 의미 있는 상위 묶음 또는 추가 깊이를 만든다. 같은 설명을 뒷받침하는 원본 근거와 이해 확인 문항은 보조 영역으로 구분하며 설명 가지의 자리를 차지하지 않는다. 원본 근거는 해당 설명 아래의 근거 묶음에서 모두 접근할 수 있어야 한다. 상한은 전체 정보의 개수를 줄이는 근거가 아니다. 본문·배경·요약의 문단 수에는 상한을 두지 않으며, 문단을 합치거나 의미 없는 하위 절을 만들어 개수를 맞추지 않는다.
- 묶음의 범위와 부모·자식 관계를 제목과 탐색 구조에 드러낸다. 근거가 부족한 분류는 읽기용 분류로 구분하고 실제 시스템의 확정된 구조처럼 주장하지 않는다. 원본 증거는 완전하게 보존하되 탐색 계층의 제한을 피하려고 거대한 설명 덩어리를 숨기지 않는다.
- 하위 설명은 기본으로 펼쳐 제공하고, 독자가 접더라도 제목과 짧은 안내에서 그 설명의 질문이나 범위를 알 수 있게 한다. 실질적인 설명의 부모는 원문 근거를 읽지 않고도 이해할 수 있어야 하며, 자식은 같은 요약을 반복하지 않고 이유·동작·조건·사례를 더한다. 결론이 여러 영역의 관계에 의존하면 그 관계를 영역별 상세보다 먼저 소개한다. 단순 자료 목록에는 빈 요약이나 고정된 깊이를 강제하지 않는다.

##### 익숙한 설명에서 정확한 동작으로 확대

- 상위 설명은 전체 의미와 판단에 필요한 관계를 제공하고, 그 질문에 필요하지 않은 내부 구조·식별자·세부 절차는 하위로 미룬다. 결론을 바꾸는 예외·미검증 사항은 상위에도 남기며 정확한 값·조건·근거는 필요한 설명 범위에서 보존한다. 상위만 읽어도 틀린 결론을 내리지 않고, 하위를 읽으면 적용 조건을 정확히 설명할 수 있어야 한다.
- 에이전트가 이미 알고 있는 사용자의 관련 업무·경험·용어·설명 선호를 적극 활용해 익숙한 비유와 출발 수준을 선택한다. 현재 지정한 독자와 선호가 우선하며, 이미 알려진 배경을 다시 묻거나 사용자의 경험을 지어내지 않는다. 관련 정보가 없으면 널리 이해할 수 있는 비유나 쉬운 직접 설명으로 진행한다. 비유를 위한 개인정보 조사나 새 사용자 프로필 저장을 요구하지 않는다.
- 비유를 사용할 때는 익숙한 요소가 실제 대상의 무엇에 대응하는지 연결하고, 비유가 더는 성립하지 않는 지점에서 실제 용어와 동작을 설명한다. 비유의 성질을 근거 없는 순서·권한·실패 보장으로 옮기지 않는다. 이미 익숙한 전문 독자에게는 이해에 도움이 되는 대응만 사용하며, 적절한 비유가 없으면 억지로 만들지 않는다.
- 하위 설명은 상위의 어느 대상이나 관계를 확대하는지 드러내고, 그 내부 책임·규칙·상태·실행을 필요한 만큼 구체화한다. 같은 수준의 분기나 원본 근거는 별도로 구분하며, 단계 수·그림 수·클릭 수를 깊이의 기준으로 삼지 않는다. 그림도 확대 대상을 유지해 상위의 요소와 하위의 내부 동작이 대응해야 한다.

#### 3. 시각 설명과 이해도 확인

##### 시각 설명

- 다이어그램 종류는 독자의 질문과 표현할 관계, 사용자가 요청한 표기법에 따라 모델이 선택한다. 예시 목록을 허용 목록으로 삼거나 특정 종류를 기본으로 강제하지 않는다. UML 클래스 관계, 상태 전이, 데이터 다중성처럼 의미가 다른 관계는 해당 표기의 의미를 보존하며 일반 박스와 화살표로 평탄화하지 않는다.
- 배포된 Mermaid가 지원하는 종류와 문법은 보고서에서 사용할 수 있어야 한다. 작성·검증·출력 경로가 별도의 좁은 종류 목록으로 선택을 제한하지 않는다. 독립 HTML은 외부 네트워크 없이 그림과 원문을 제공하며 원문의 실행 코드나 콜백을 실행하지 않는다. 구문 검증, 실제 그림 생성과 의미 검토는 구분하고, 그림 생성 대기·실패를 성공으로 표시하지 않는다.
- 개요부터 가장 깊은 세부 절까지, 설명할 책임·조건·상태·시간 순서·대응 관계를 근거와 전달 형식 안에서 표현할 수 있으면 해당 설명에 그림을 기본으로 제공한다. 상위 그림이 있다는 이유로 하위의 유용한 그림을 생략하지 않는다. 그림 수와 깊이별 배분을 고정하지 않으며, 단순 사실을 꾸미거나 같은 그림을 반복해 개수를 채우지 않는다.
- 전체 시스템과 여러 단계의 과정은 가능한 경우 짧은 배경과 답 뒤, 세부 설명 앞에 개요 그림을 둔다. 하위 설명과 그림은 개요의 같은 책임이나 관계를 확대한다. 여러 참여자의 요청·응답·시간 순서는 Mermaid 시퀀스 다이어그램, 흐름·분기·상태·데이터 관계는 그 관계에 맞는 그림으로 표현한다. top-down·C4·drill-down 요청도 이 기본값을 따르며 그림을 필수 산출물로 만들지는 않는다.
- 사용자의 그림 제외 요청과 전달 형식 제약이 우선한다. 근거가 부족하거나 그림을 제공할 수 없으면 확인한 내용을 글과 근거로 설명하며, 해석에 영향을 주는 한계는 밝힌다. 그림 부재만으로 보고서 생성·검증·전달을 거부하거나 완료를 차단하지 않으며, 생략 승인을 별도로 요구하지 않는다. 그림이 없는 보고서도 같은 정확성·구조·근거 기준으로 검토한다.
- 그림은 근거에 있는 참여자·관계·순서·상태·실패 경로를 보존하고, 옆에 읽는 법과 설명 범위를 둔다. 지원하지 않는 구문은 같은 관계를 보존하는 표현으로 바꾸거나 렌더링 한계와 원문을 표시한다. 실제로 렌더링되지 않은 그림을 성공했다고 주장하지 않는다. 그림의 부재를 허용하는 정책은 제공한 그림의 정확성·구문 검증을 생략하는 근거가 아니다.

##### 핵심 내용과 문항 수

- 핵심 내용을 이해하는 데 도움이 되는 퀴즈 생성을 강하게 권고한다. 사용자가 명시적으로 요청하면 생성하고 제외하면 생략한다. 그 외에는 독자의 목적과 추가 이해 효과에 따라 별도 승인이나 필수 생략 기록 없이 생략할 수 있으며, 퀴즈 부재만으로 보고서 전달을 차단하지 않는다. 생성할 때 문항 수는 전체 보고서에서 1개 이상 5개 이하이며, 도메인마다 최대치를 다시 적용하거나 개수를 채우려고 문제를 추가하지 않는다.
- 각 문항은 문서에 설명된 핵심 개념·인과관계·적용 조건·중요한 선택 중 하나를 상황에 적용하는 중간 난이도 문제다. 정답과 해설은 문서 및 그 근거로 확인할 수 있어야 한다. 문서 밖의 지식, 사소한 이름·줄 번호 암기, 말장난과 함정을 요구하지 않는다.
- 각 문항은 서로 다른 선택지 정확히 4개와 정답 정확히 1개를 가진다. 오답은 핵심 내용에 관한 그럴듯한 오해를 반영하며 문장 길이나 표현으로 정답을 드러내지 않는다.
- 질문은 답에 필요한 설명과 하위 설명 뒤, 해당 범위의 상세 근거 앞에 배치하며 HTML과 Markdown에서 이 의미 순서를 유지한다. 관련 하위 설명이 접혀 있으면 문항에서 그 범위로 돌아갈 수 있어야 한다. 문항은 실제 주제에 귀속시키고 설명 가지 수와 별도로 전체 1~5개 상한을 적용한다. 독자는 문항과 관련 설명을 연결해서 읽을 수 있어야 한다.

##### 단계별 자가 확인

- HTML은 질문과 짧은 회상 안내를 먼저 보여준다. 사용자가 선택지 보기를 요청한 뒤 네 선택지를 공개한다. 하나를 선택하면 자가 확인 전에 선택 이유를 한 문장으로 설명해 보라는 안내를 제공하며 별도 입력이나 채점을 요구하지 않는다.
- 사용자가 정확히 하나의 답을 선택하고 자가 확인을 요청한 뒤에만 정답, 선택에 대한 중립적인 피드백, 해설과 근거를 공개한다. 점수·등급·축하·능력 평가를 사용하지 않는다.
- 전체 질문 중 핵심 질문 1개 이상 2개 이하를 나중에 다시 확인할 대상으로 표시한다. 전체 질문이 한 개면 그 질문을 표시한다. 재확인 안내에는 정확한 시간 간격, 알림, 완료 이력이나 진행 상태의 영속 저장을 추가하지 않는다.
- 인쇄물은 질문과 네 선택지를 포함하되 정답·피드백·기존 선택 표시·조작 버튼을 제외한다. Markdown이나 텍스트에서도 질문·선택지와 정답·해설을 분리하며 자동 채점이나 숨김 동작을 지원한다고 주장하지 않는다.

##### 판정과 완료의 경계

보고서에 퀴즈를 포함하는 것과 대화형 퀴즈를 실행하는 것은 구분한다. 일반 완료 응답은 보고서 위치와 결과를 전달하고 퀴즈를 자동 시작하지 않는다. 사용자가 명시적으로 요청하면 한 번에 한 문항씩 진행하며, 오답에는 근거와 부족한 개념을 설명한 뒤 같은 문항을 다시 제시한다.

퀴즈는 이해도를 높이고 인지부하를 줄이기 위한 지원이다. 생성 여부나 정답 선택만으로 학습 효과를 측정했다고 주장하지 않는다. 퀴즈는 원래 작업의 승인, 코드 적합성 판정이나 완료를 차단하지 않으며 진행·통과 상태를 영속 권위로 저장하지 않는다. 구현 리뷰의 코드 판정과 사람이 변경을 이해했다는 판정은 별도로 유지한다.

#### 4. 품질 검토와 완료

일반 전달의 완료 기준은 최신 내용의 의미 검토, 구조·근거·링크와 생성 파일의 정적 확인이다. 다이어그램을 포함하면 실제 그림 출력이 생성되고 원문과의 대응이 유지되는지 확인한다. 브라우저 화면·상호작용·실제 인쇄 검증은 사용자가 요청한 경우에 수행하며, 미수행 범위는 구분해 밝힌다. 요청된 검증이 실패하거나 차단되면 완료로 주장하지 않는다. 기본 브라우저 열기는 전달 단계이며 시각 검증을 대신하지 않는다.

문단은 주체·논점·예시가 바뀌는 의미 경계에서 나눈다. 조건과 결과는 함께 읽고 문장마다 강제 줄바꿈하지 않는다. 자동 줄바꿈은 화면 폭·행간·문단 여백으로 조절하며 수치·단위·부정·원문 의미를 훼손하지 않는다. 제목·표·그림과 인쇄에서의 분리도 검토한다.

중요한 수식은 입력·단위·가정, 대입·계산과 결과 해석을 함께 제공하고 검산한다. 문체 비교는 제공된 실제 참고 자료와 현재 선호에 근거하며 블로그 전용 형식을 일반 보고서에 강제하지 않는다.

문서 품질의 High·Medium·Low와 보고 대상 시스템의 finding severity를 구분한다. 문장·흐름, 주제·근거, 반복·문체를 검토하고 수정을 허용한 작업은 최신 전체 결과의 High·Medium 문제가 없을 때까지 재검토한다. 검토 전용 요청에서는 수정하지 않는다. 검토를 통과하려고 시스템 위험을 삭제하거나 등급을 낮추지 않는다.

- 근거 없는 과장, 상투적 도입, 장식용 용어, 반복 결론·대조와 의미 없는 연결문을 문맥에 따라 수정한다. 같은 표현이 실제 대화나 논리 연결 역할을 하면 보존한다.
- 각 부분에서 행위자, 조건, 동작, 관찰 결과와 필요한 판단이 드러나게 쓰며 낯선 용어는 처음 필요한 곳에서 설명한다. 사실, 근거 있는 해석과 제안을 구분한다.
- 최종 전달물의 제목·목차·문단·표·다이어그램·접힌 상세를 실제 읽기 순서로 검토한다. 구조 검증이나 금지어 검색만으로 AI Slop 제거와 이해도 검토를 통과했다고 판단하지 않는다.
- 접힌 상태에서 전체 답·한계·다음 선택을 이해할 수 있는지, 가지를 하나씩 펼칠 때 같은 대상의 내부 구조나 동작이 새로 드러나는지 확인한다. 펼친 세부 절에서도 필요한 관계가 그림으로 설명되는지, 상위 그림을 반복하거나 문장 하나를 장식하는 데 그치지 않는지 검토한다. 평가는 동일한 사실을 보존하는 정상 예시와 상위의 세부사항 과다 노출·같은 수준의 분기를 깊이로 오인·비유의 잘못된 확장·사용자 배경 날조·상위 요약 반복·선행 설명 누락·원문 의존 같은 실패 예시를 구분하며 특정 목차를 정답으로 삼지 않는다. 형식 검사나 모델 평가 통과만으로 실제 독자의 학습 효과를 주장하지 않는다.
- 의미·근거·읽기 흐름을 방해하는 중대한 문제는 수정 후 다시 검토한다. 확인할 수 없는 근거는 한계로 표시한다. 내용 검토와 형식별 구조·렌더링 검증의 실제 수행 범위를 결과에 맞게 보고한다.

### Alternatives

1. **스킬별 독립 지침 유지**
   - 장점: 기존 작성 흐름을 적게 바꾼다.
   - 단점: 형식과 진입 경로마다 읽기 방식과 품질이 달라진다.
2. **평면적인 고정 양식**
   - 장점: 일정한 위치에서 정보를 찾을 수 있다.
   - 단점: 도메인과 복잡도가 달라도 긴 동급 목록이 생긴다.
3. **공통 작성 기능과 도메인별 확대**
   - 장점: 독자는 필요한 도메인과 수준까지 읽을 수 있다.
   - 단점: 적절한 범위를 나누고 형식별 결과를 검증하는 비용이 필요하다.

생성 범위는 명시적 요청과 이해에 필요한 복잡도를 기준으로 선택한다. 모든 기술 설명·리뷰를 보고서로 만들면 단순한 답에도 파일 생성과 열기 비용이 생기고, 명시적 요청에만 반응하면 복잡한 내용을 이해하는 데 필요한 지원을 놓친다. 복잡한 내용은 자동 생성하고 단순한 내용은 대화로 전달하며, 판단이 애매할 때만 확인하는 방식을 채택한다.

이해도 퀴즈도 공통 작성 기능에서 생성한다. 구현 리뷰에만 퀴즈를 두면 다른 보고서의 핵심 내용을 확인할 수 없고 생성 조건이 진입 경로마다 달라진다. 강한 권고는 공통 생성의 이점을 유지하면서 보고서의 목적에 따라 생략할 여지를 준다. 모든 보고서에 생성을 강제하면 학습이 주목적이 아닌 경우에도 문항과 오답을 검토하는 비용이 추가된다.

배포 범위는 adr-writer 단독 제공을 선택한다. 양쪽 플러그인에 포함하면 어느 플러그인에서든 보고서를 작성할 수 있지만, 함께 설치할 때 같은 스킬과 지침이 중복된다. adr-writer 단독 제공은 리뷰 기능과 보고서 작성 책임을 한곳에 두며, alps-writer만 설치한 사용자에게는 보고서 기능을 제공하지 않는다.

## Consequences

- 단순한 설명은 대화에서 마치고, 복잡한 내용은 별도 요청 없이 보고서로 이해할 수 있다. 경계가 애매한 요청에는 전달 방식을 확인하는 한 차례의 대화가 필요하다. 복잡도 판단은 요청 이름이나 길이 대신 독자의 이해에 필요한 관계와 근거를 기준으로 검토한다.
- 독자가 한 번에 해석해야 하는 책임과 관계를 관리한다. 가능한 관계는 그림으로 설명하고, 그림을 제공하기 어려운 경우에도 글과 근거로 전달한다. 검증 결과와 원본 근거를 보존하며 같은 내용을 여러 요약·표·그림으로 반복하지 않는다.
- 두 플러그인을 함께 설치해도 보고서 스킬과 지침은 한 번만 노출된다. alps-writer만 설치한 사용자가 보고서 기능을 원하면 adr-writer 또는 독립 보고서 스킬을 별도로 설치해야 한다.
- 기존의 평면적인 보고서 작성 지침·렌더러·검증 규칙은 공통 계약에 맞춰 조정해야 한다. 퀴즈를 생성한 보고서는 핵심 내용에 맞는 문항과 단계별 정답 공개를 제공한다. 생성은 강한 권고이며 문항 수를 제한하고 생성·풀이를 기본 완료 조건으로 강제하지 않는다.
- 사람의 이해와 생산성 향상은 목표이며, 형식 검사 통과만으로 실제 향상 정도를 측정했다고 주장하지 않는다.
