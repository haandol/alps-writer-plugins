# ADR 0001: 플러그인별 공개 MCP 도구와 스킬 수 제한

Date: 2026-11-14

## Status

Accepted (2026-11-14)

## Purpose

에이전트는 도구와 스킬을 선택하기 위해 공개된 이름과 설명을 문맥에 읽는다. 유사한 작업과
문서 프로필마다 진입점을 늘리면 같은 설명이 반복되고, 모든 작업을 한두 개로 묶으면 입력과
역할을 구별하기 어렵다. 사용자는 기능을 보존하면서 각 플러그인의 MCP 도구는 5개 이하,
공개 스킬은 10개 이하로 유지하기를 원한다.

## Decision Drivers

- 공개 정의의 반복을 줄이되 호출자가 작업의 대상과 효과를 구별할 수 있어야 한다.
- 수를 맞추기 위해 기능을 제거하거나 승인·검증 경계를 약화하지 않아야 한다.
- 이미 상한 안에 있는 독립 기능은 불필요하게 통합하지 않아야 한다.
- 각 플러그인은 단독 설치에서 필요한 세부 절차를 자체적으로 제공해야 한다.

## Decision

각 플러그인은 MCP(Model Context Protocol) 도구를 최대 5개, 공개 스킬을 최대 10개 제공한다.
두 상한은 별도로 센다. 같은 대상의 유사 작업은 작업 선택자로 묶고, 상세 절차는 필요한 때
읽는 플러그인 내부 자료로 제공한다. 공개 별칭도 개수에 포함한다.

ALPS Writer의 도구는 템플릿 조회, 문서 관리, 본문 편집, 용어집, 내보내기로 구분한다.
문서 프로필은 Full·Lite 중 선택하고 기존 문서는 원본에서 판별한다. ADR Writer의 독자
프로필 관리는 리포트 작성의 관련 작업으로 제공한다. 스킬 선택만으로 보고서를 만들거나
독자 프로필을 갱신하지 않고 사용자가 요청한 작업을 수행한다.

이 구분은 작업 대상별 선택을 유지하면서 중복 정의를 줄인다. 통합한 개별 도구와 스킬의
이전 이름은 공개 별칭으로 남기지 않는다. 배포되는 호출 안내는 통합된 이름과 입력을 사용한다.

### Requirement contract

| 의무                                                                                                         | 관찰 가능한 검증 기준                                                                                     |
| ------------------------------------------------------------------------------------------------------------ | --------------------------------------------------------------------------------------------------------- |
| R1. 각 플러그인의 공개 MCP 도구는 5개 이하다.                                                                | 개별 플러그인의 도구 목록을 조회하면 별칭을 포함해 5개를 넘지 않는다.                                     |
| R2. 각 플러그인의 공개 스킬은 10개 이하다.                                                                   | 각 설치 단위의 공개 스킬을 발견하면 10개를 넘지 않으며 빌드·동기화 후에도 유지된다.                       |
| R3. ALPS는 Full·Lite의 개요, 섹션 목록, 개별·전체 템플릿, 작성 가이드를 제공한다.                            | 두 프로필의 모든 조회가 가능하고 예시는 기본 제외·명시적 요청 시 포함된다.                                |
| R4. ALPS는 두 프로필의 생성, 열기, 상태, 본문 읽기·저장, 용어 읽기·저장, Markdown 반환·파일 저장을 제공한다. | 두 프로필에서 모든 작업을 호출해 기존 내용과 결과를 보존한다.                                             |
| R5. 작업은 명시적으로 선택하며 작업별 필수 입력과 유효 범위를 검증한다.                                      | 누락·알 수 없는 작업·관련 없는 입력·잘못된 프로필 조합은 원본 변경 전에 실패한다.                         |
| R6. 생성은 프로젝트 이름·생성 위치·프로필을 필수로, 기존 문서 작업은 원본 문서를 필수로 지정한다.            | 사전 열기 없이도 지정한 문서만 사용하고 다른 요청의 대상으로 전환하지 않는다.                             |
| R7. 본문 저장은 섹션·항목·제목·내용을, 용어 저장은 용어·정의를 요구한다.                                     | 빠진 필수 입력은 거부하고, 읽기·저장 범위와 기존 검증이 유지된다.                                         |
| R8. 기존 문서 형식, 프로필별 작성·완료, 승인·개별 저장과 실패 시 원본 보존을 유지한다.                       | 통합된 호출로 기존 문서를 작성·재개·내보내기하며 승인 없는 계약 저장을 안내하지 않는다.                   |
| R9. 독자 프로필 생성·갱신·보기·수정·삭제 기능과 명시적 요청에 따른 세션 읽기 경계를 유지한다.                | 리포트 스킬에서 각 프로필 작업에 접근하며 프로필 작업이 불필요한 보고서·퀴즈를 만들지 않는다.             |
| R10. 단계별 상세는 해당 작업에서만 읽고 각 플러그인은 필요한 내부 자료를 단독 설치에 포함한다.               | 한 작업을 시작할 때 관련 없는 모드의 상세를 모두 읽지 않으며 형제 플러그인의 설치 경로에 의존하지 않는다. |
| R11. 공개 안내는 실제 호출과 일치하고 쓰기 가능한 도구를 읽기 전용으로 표시하지 않는다.                      | 안내대로 전체 기능에 접근할 수 있으며 제거된 이름의 호출이나 잘못된 부작용 표시에 의존하지 않는다.        |
| R12. 기능별 도구 노출보다 전체 도구 정의의 텍스트량을 줄인다.                                                | 같은 직렬화 기준에서 전체 도구 목록 크기가 감소하고 필수 작업 접근은 모두 유지된다.                       |

### Alternatives

- **기능별 진입점 유지:** 개별 동작은 분명하지만 반복되는 정의와 공개 스킬 수가 상한을 넘는다.
- **한두 개의 범용 진입점:** 개수는 작지만 서로 다른 작업의 역할과 입력을 구별하기 어렵다.
- **대상별 통합과 서로 다른 상한:** 도구는 5개, 스킬은 10개까지 허용해 동작의 구분과 문맥 비용을 함께 관리한다.

## Consequences

### Positive

- 기능을 유지하면서 공개 정의의 중복과 초기 선택 부담을 줄인다.
- 상세 절차와 승인·검증 규칙은 필요한 작업에서 계속 사용할 수 있다.

### Negative

- 통합된 도구나 스킬의 이전 이름을 사용하던 호출자는 호출 방식을 바꿔야 한다.
- 작업별 필수 입력을 정확히 설명하고 검증해야 한다.

### Risks

- 개수만 줄이고 모든 상세를 한 번에 읽으면 문맥 절약이 되지 않는다. 공개 정의와 조건부 로딩을 함께 확인한다.
- 동기화가 제거한 공개 스킬을 다시 만들 수 있다. 배포 단위의 발견 결과로 상한을 검증한다.
