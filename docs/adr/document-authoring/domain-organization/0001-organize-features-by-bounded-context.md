# ADR 0001: 프로젝트 형태와 독립적으로 업무 경계와 기능별 문서를 구성

Date: 2026-09-30

## Status

Accepted (2026-09-30)

## Purpose

개발자는 기존 프로젝트의 코드 구조를 이해한 뒤 기능과 설계 결정을 정리해야 한다. 저장소가 하나인지 여러 개인지, 애플리케이션이 하나의 실행 단위인지 여러 서비스인지에 따라 조사 범위와 근거 위치는 달라진다. 그러나 이 배치 구조를 문서 분류에 그대로 사용하면 같은 사용자 기능이 화면, 서버와 데이터 계층에 흩어진다.

제품 기획과 설계 기록은 DDD(도메인 주도 설계)의 바운디드 컨텍스트, 즉 같은 업무 용어와 규칙이 적용되는 경계를 기본으로 삼는다. 그 안에서 하나의 사용자 행동과 결과를 끝까지 연결하는 버티컬 슬라이스 또는 사용자 스토리를 기능 단위로 사용한다. 기존 코드가 계층별로 나뉘어 있어도 문서는 기능의 목적과 계약을 함께 읽을 수 있어야 한다.

## Decision Drivers

- 저장소와 배포 구조가 달라도 같은 업무 기능의 계약을 같은 단위로 이해할 수 있어야 한다.
- 하나의 기능이 여러 코드 계층이나 서비스에 걸쳐 있어도 목적, 규칙과 결과가 분산되지 않아야 한다.
- 업무 경계를 알 수 없는 부분은 구현 디렉터리로 대신하거나 근거 없이 확정하면 안 된다.
- 제품 기획, ADR 작성과 기존 프로젝트 가져오기가 동일한 기능 경계를 사용하되 각 문서의 해상도와 독립성을 유지해야 한다.

## Decision

작성 하네스는 프로젝트의 저장소·실행 구조를 먼저 조사하고, 업무 용어와 규칙의 소유 경계를 근거로 바운디드 컨텍스트를 식별한다. 모노레포는 여러 구성 요소를 한 저장소에서 관리하는 형태이고, 멀티레포는 여러 저장소에서 관리하는 형태다. 모노리스는 애플리케이션을 하나의 주된 실행·배포 단위로 운영하는 형태이고, 마이크로서비스는 여러 서비스로 나누어 운영하는 형태다. 저장소 구성과 실행·배포 형태는 서로 다른 축으로 판정한다.

문서의 기능 분류는 항상 바운디드 컨텍스트와 사용자 결과를 따른다. 서비스 수, 저장소 수 또는 코드 폴더 이름만으로 업무 경계를 결정하지 않는다. 한 컨텍스트가 여러 서비스나 저장소에 걸칠 수 있고, 하나의 모노리스가 여러 컨텍스트를 포함할 수 있다.

제품 기획은 기능의 사용자 문제와 관찰 결과를 설명하고, ADR은 같은 기능 안의 지속적인 결정과 요구사항을 설명한다. 서로 독립적으로 바뀌는 결정은 같은 기능 아래 여러 ADR로 남을 수 있다. 여러 기능이 공유하는 독립 계약은 실제 공유 범위에서 한 번 소유하며, 이를 기술 계층별 문서 분리의 근거로 사용하지 않는다.

### Requirement contract

#### 프로젝트 조사

| 의무                                                                                               | 관찰 가능한 검증 기준                                                                                                                                                     |
| -------------------------------------------------------------------------------------------------- | ------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| 기존 프로젝트를 입력받은 작성 경로는 기능을 분류하기 전에 저장소 구성과 실행·배포 형태를 조사한다. | 모노레포·멀티레포 여부와 모노리스·마이크로서비스 여부를 별도 축으로 설명하며, 혼합 형태와 미확인 상태도 그대로 표시한다.                                                  |
| 프로젝트 조사에는 접근 가능한 근거의 범위를 표시한다.                                              | 관련 저장소를 읽지 못했다면 전체 멀티레포 시스템을 조사했다고 주장하지 않는다. 코드가 없는 신규 기획은 현재 구현을 추정하지 않고 제공된 제품 정보로 경계 후보를 제시한다. |
| 저장소·배포 구조와 바운디드 컨텍스트를 자동으로 일대일 대응하지 않는다.                            | 여러 서비스가 하나의 업무 규칙을 공유하는 경우와, 단일 애플리케이션에 서로 다른 업무 모델이 있는 경우를 각각 표현할 수 있다.                                              |

#### 기능 문서 구성

| 의무                                                                                            | 관찰 가능한 검증 기준                                                                                                                                  |
| ----------------------------------------------------------------------------------------------- | ------------------------------------------------------------------------------------------------------------------------------------------------------ |
| 제품 기획과 ADR의 기능 분류는 바운디드 컨텍스트를 기본으로 사용한다.                            | 별도 DDD 요청이 없어도 기능이 업무 용어와 규칙의 경계 안에서 설명된다. 경계 후보는 근거와 함께 제시하며 중요한 불확실성은 확인 전까지 확정하지 않는다. |
| 각 기능은 하나의 사용자 스토리 또는 버티컬 슬라이스로 구성한다.                                 | 사용자·운영자·외부 시스템의 행동이나 사건에서 시작해 관련 처리와 관찰 결과까지 추적할 수 있다. 화면이 없는 기능에 화면 단계를 발명하지 않는다.         |
| 문서를 프런트엔드, 백엔드, API, 데이터베이스 등 기술 계층별 기능으로 나누지 않는다.             | 같은 기능의 화면·요청 처리·데이터 규칙이 하나의 기능 범위에서 설명되며, 코드가 계층별이어도 문서 분류가 그 구조를 복제하지 않는다.                     |
| 하나의 ADR은 하나의 지속적인 결정을 소유한다.                                                   | 같은 기능의 독립 결정은 여러 ADR로 나뉠 수 있고, 여러 기능의 공유 계약은 한 소유자에 남으며 불필요한 복제가 없다.                                      |
| ADR 색인의 분류 키는 바운디드 컨텍스트 또는 바운디드 컨텍스트와 기능의 최대 두 단계로 구성한다. | 단일 기능 컨텍스트는 평평한 구성을 유지할 수 있고, 여러 기능은 컨텍스트 아래 기능으로 나뉜다. 계층 이름이나 세 번째 분류 단계가 생기지 않는다.         |

#### 작성 경로와 해상도

| 의무                                                                                                                 | 관찰 가능한 검증 기준                                                                                                                   |
| -------------------------------------------------------------------------------------------------------------------- | --------------------------------------------------------------------------------------------------------------------------------------- |
| 같은 분류 원칙을 Full·Lite 제품 기획, 직접 ADR 작성, 제품 기획에서 ADR로 인계, 기존 프로젝트 가져오기에 적용한다.    | 어느 진입점에서도 기능 분류가 기술 계층으로 돌아가지 않는다. 각 플러그인은 자기 범위의 로컬 지침으로 동작한다.                          |
| 기능 인계는 이미 확인된 업무 경계를 보존하고, 경계가 없거나 충돌하면 근거 있는 후보를 제시해 필요한 의미를 확인한다. | 별도 그룹 요청이 없다는 이유로 경계 파악을 생략하지 않으며, 불명확한 경계를 임의로 확정하지 않는다. 확인된 분류를 다시 질문하지 않는다. |
| 제품 기획과 ADR은 기존 문서 형식과 해상도를 유지한다.                                                                | Full과 Lite의 정해진 절 및 C4 다이어그램 범위가 유지되고, 업무 분류를 이유로 내부 코드 구조가 제품 기획에 추가되지 않는다.              |
| 업무 경계 식별에 부가적인 도메인 등급 분류를 필수로 요구하지 않는다.                                                 | 핵심·지원·범용 등급을 답하지 않아도 업무 경계와 기능 문서를 작성할 수 있다.                                                             |

#### 변경과 검증 경계

| 의무                                                                                                | 관찰 가능한 검증 기준                                                                                                                        |
| --------------------------------------------------------------------------------------------------- | -------------------------------------------------------------------------------------------------------------------------------------------- |
| 문서 분류 요청은 대상 애플리케이션의 코드 구조 변경을 허가하지 않는다.                              | 계층형 코드를 기능별로 설명하는 작업이 코드 이동이나 서비스 재분할로 이어지지 않는다.                                                        |
| 기존 문서를 옮기거나 합치는 변경은 해당 문서 관리 경로의 승인 및 보존 규칙을 따른다.                | 작성 하네스의 기본 분류 변경만으로 기존 ADR이 이동·삭제·재번호화되지 않는다.                                                                 |
| 하네스는 근거 있는 경계와 기능별 결과를 검사하고 특정 탐색 도구나 내부 실행 순서를 강제하지 않는다. | 다른 탐색 방법으로도 같은 계약을 지키는 결과를 만들 수 있으며, 모든 요청에서 전체 저장소를 다시 조사하지 않고 유효한 현재 문맥을 재사용한다. |

### Alternatives

1. **저장소·서비스·기술 계층을 문서 분류로 사용**
   - 장점: 현재 코드 위치와 문서 위치를 쉽게 대응한다.
   - 단점: 사용자 기능이 여러 문서에 흩어지고 코드 배치 변경이 문서 분류 변경을 유발한다.

2. **업무 경계 안에서 사용자 기능별로 구성**
   - 장점: 프로젝트 형태와 독립적으로 목적과 계약을 읽을 수 있고 제품 기획에서 ADR까지 기능 의미가 이어진다.
   - 단점: 코드에서 명확하지 않은 업무 경계는 근거 조사와 사용자 확인이 필요하다.

3. **사용자가 명시한 경우에만 업무 경계를 적용**
   - 장점: 경계가 분명하지 않은 프로젝트에서 초기 질문이 적다.
   - 단점: 진입점이나 사용자의 분류 지식에 따라 기능 조직이 달라지고 계층별 문서가 남는다.

## Consequences

### Positive

개발자는 프로젝트의 실제 구조를 이해하면서도 사용자 기능의 계약은 한 범위에서 읽을 수 있다. 제품 기획과 ADR의 기능 의미가 이어지고, 구현 구조가 달라져도 문서의 업무 경계를 재사용할 수 있다.

### Negative

업무 용어와 책임이 섞인 프로젝트는 경계 후보를 검토해야 한다. 기존 폴더만 복사하는 방식보다 초기 분석이 필요하며, 미확인 경계는 질문으로 남는다.

### Risks

DDD 용어만 붙이고 실제로 서비스나 기술 계층을 그대로 복제할 수 있다. 검증은 이름뿐 아니라 기능의 행동·규칙·결과가 한 범위에서 이어지는지 확인해야 한다. 반대로 모든 기능을 억지로 한 문서에 모으면 독립된 결정이 섞일 수 있으므로 결정 소유자 기준을 함께 적용한다.
