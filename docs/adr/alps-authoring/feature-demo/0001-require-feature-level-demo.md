# ADR 0001: Feature 의도를 완료 판정과 개선 평가에 연결

Date: 2026-08-17

## Status

Proposed

## Purpose

Feature 작성자는 사용자가 어떤 문제를 해결하려는지와 어떤 결과를 얻어야 하는지를 구현 전에 확인해야 한다. 결과를 서술한 체크리스트만으로는 평가기가 어떤 상황의 어떤 증거를 무슨 규칙으로 판정할지 알기 어렵다. 각 Feature는 의도에서 평가 기준을 도출하고, 적용 상황·관찰 증거·검증 수단·판정 규칙을 연결해 초기 구현의 완료를 확인할 수 있게 한다.

Section 3은 MVP의 전체 데모 여정을 설명하고 Section 7은 각 Feature를 수직 슬라이스로 상세화한다. 사용자는 각 Feature가 전체 데모에서 어떤 역할을 하는지 확인할 수 있어야 한다.

별도 Feature Demo에 사전 조건, 사용자 행동, 관찰 결과, 실패 시나리오와 성공 판정을 다시 기록하면 Section 7의 User Flow, 오류 처리와 Evaluation Rubric를 중복한다. 같은 제품 행동을 두 곳에 유지하면 작성 비용과 드리프트 위험이 함께 증가한다.

지표를 개선할 때도 원래 사용자 목적을 지켜야 한다. 의미 있는 반대 방향 지표를 함께 제안하되, 지표의 개수를 채우기 위해 관련 없는 조건을 만들거나 자율 진행을 막지 않는다.

## Decision Drivers

- Builder는 각 Feature가 전체 MVP 데모에 기여하는 지점을 빠르게 확인할 수 있어야 한다.
- 평가 기준은 구현 전에 의도한 결과와 위반을 구분할 수 있어야 한다.
- Section 7은 같은 사용자 행동을 여러 subsection에 반복하지 않아야 한다.
- 데모 연결은 제품 행동 수준을 유지하고 구현 계획이나 테스트 절차로 내려가지 않아야 한다.
- 상세한 데모 설명은 기존 User Flow, 오류 처리와 Evaluation Rubric에서 복구할 수 있어야 한다.

## Decision

Section 7의 각 Feature는 User Story의 의도를 7.x.6 Evaluation Rubric에 연결한다. Rubric은 Ideal Cases, Edge Cases, Automated Evaluation Metrics 순서로 정상 동작, 경계·오류 상황과 자동 평가 지표를 설명한다. 사례는 무엇을 실행하고 어떤 결과를 확인할지, 지표는 해당 결과를 어떻게 계산·판정할지 연결한다. 마지막에는 전체 데모에서 확인할 결과와 역할을 잇는 **Demo outcome** 한 줄을 기록한다.

User Story는 대상 사용자, 해결할 문제와 얻어야 할 결과를 설명한다. Evaluation Rubric는 독립적인 평가 의무마다 기준과 필수·관찰용 구분, 적용 상황과 입력, 관찰할 증거, 검증 수단과 판정 규칙을 연결한다. Ideal Cases와 Edge Cases는 기준·용도, 적용 상황·입력, 관찰 증거, 검증 수단·판정 규칙을 보존한다. Automated Evaluation Metrics는 관련 사례와 모집단, 계산·단위·방향·관찰 조건, 검증 수단과 필수 또는 관찰용 의미를 연결하고, 유용한 경우 같은 목적을 보호하는 eval metric과 tension metric을 짝지어 제시한다. 지표가 없거나 관찰이 부족한 결과를 0이나 통과로 바꾸지 않는다. 새로운 저장 스키마나 별도 평가 문서를 만들지 않는다. 기존 문서의 Acceptance Criteria 제목은 같은 평가 영역으로 읽으며 이름 차이만으로 완료된 문서를 다시 승인·저장하거나 자동 마이그레이션하지 않는다. 작성자는 이 연결을 Feature 승인 전에 제시하며, 이미 확인한 의도와 요구사항은 재질문하지 않는다. 긴 User Flow를 복제하지 않으면서 판정에 필요한 최소 조건은 해당 기준에서 읽을 수 있어야 한다.

명확한 값·상태·순서의 비교는 코드 검사, 의미 해석은 좁은 기준의 LLM 평가, 실제 사용자 결과는 해당 진입점의 동작 증거로 확인한다. 화면 기능에는 필요한 화면 흐름을 검증하며 API나 CLI 제품에는 그 진입점을 사용한다. 단위 테스트·빌드·화면의 존재만으로 다른 의무의 충족을 대신하지 않는다. 이 구분은 증거의 종류이며 구체적인 도구·명령·평가기 구현은 코드 수준에서 정한다. LLM의 의미 판단 자체가 항상 같다고 보장하지 않고, 관찰과 기준별 판정이 고정됐을 때의 최종 집계 규칙을 명확히 한다.

Demo outcome는 Section 3 전체 여정에서 해당 Feature가 담당하는 역할과 사용자가 관찰할 완료 결과를 한 문장으로 연결한다. 데모의 순서, 오류와 성공 조건은 기존 User Flow, edge case·error handling과 Evaluation Rubric를 사용한다. 별도 `7.x.7 Feature Demo` subsection은 만들지 않는다.

사용자가 상세 데모 절차를 요청하면 모델은 Section 3과 해당 Feature의 기존 subsection에서 일시적으로 조합해 보여준다. 파생된 절차는 ALPS 문서의 별도 권위로 저장하지 않는다.

### Requirement contract

#### 완료 판정과 개선 신호

평가는 사용자 목적을 달성했는지 판단하기 위해 사용한다. 평가 점수만 높이면서 어려운 요청을 제외하거나 실패를 숨기는 결과는 개선으로 인정하지 않는다. 완료 판정은 알려진 요구사항과 대표 상황으로 시작하고, 실제 사용에서 확인한 실패로 보완한다.

| 의무                                                                                                             | 관찰 가능한 검증 기준                                                                                                                      |
| ---------------------------------------------------------------------------------------------------------------- | ------------------------------------------------------------------------------------------------------------------------------------------ |
| 완료 판정과 지속 개선의 판단을 구분한다.                                                                         | 알려진 정상·실패 사례로 초기 구현을 확인하며 데모 통과를 운영 개선의 증명으로 표시하지 않는다.                                             |
| 주 지표를 제안하면 같은 사용자 목적을 보호하는 tension metric 후보를 적극 검토하고 의미 있는 경우 함께 제안한다. | 빠른 처리만 늘려 오답이나 부당 거절이 늘어나는 등 주 지표의 편법을 발견할 수 있는 후보를 설명한다.                                         |
| Tension metric의 개수와 존재는 필수가 아니다.                                                                    | 적절한 지표가 없거나 정량화가 부적절하면 관찰 가능한 실패·반례를 활용할 수 있으며, 지표 부재만으로 작성·승인·저장·구현·개선을 막지 않는다. |
| 관찰용 신호와 필수 수용·채택 조건을 구분한다.                                                                    | 관찰용 지표의 변화만으로 자동 실패를 선언하지 않으며, 필수로 확정한 보호 조건과 기존 안전·권한 계약은 주 지표 상승으로 상쇄하지 않는다.    |
| 판정에 쓰는 지표는 대상·집계·분모·관찰 기간·제외 규칙을 해당 판단에 필요한 만큼 명확히 한다.                     | 평가 대상을 빼거나 실패를 재분류해 얻은 점수 상승을 같은 조건의 개선으로 비교하지 않는다.                                                  |
| 필수 조건의 값과 판단 규칙은 근거와 함께 기존 승인에 포함한다.                                                   | 예시 수치가 기본 요구사항이 되지 않으며 필수 증거가 미확인이면 충족했다고 표시하지 않는다.                                                 |
| 실제 실패와 추정·가상 사례를 구분하고 새 제품 판단은 사람이 확인한다.                                            | 기존 계약 위반은 회귀 사례로 보완하며, AI가 만든 라벨을 사람의 확인 결과로 부르거나 새 정책으로 확정하지 않는다.                           |
| 의미 판정이 필요하면 실패 유형별 기준과 확인된 사례로 실패 누락·오탐을 함께 검토한다.                            | 포괄적인 평균 일치율만으로 판정기를 신뢰하거나 정적 검사만으로 실제 행동을 입증하지 않는다.                                                |

새 subsection이나 별도 평가 계획 문서는 요구하지 않는다. 수용·개선 조건의 의도와 정확한 규칙은 인계 시 ADR이 소유하고 실제 trace·평가 데이터·평가기 구현·실행 결과는 구현·검증 자료로 관리한다.

각 기준은 충족을 입증한 결과, 관찰된 위반, 증거 부족·실행 또는 판정 오류를 구분한다. 알려진 필수 위반이 있으면 통과할 수 없고, 위반이 확인되지 않았더라도 필수 증거가 부족하면 미확인으로 남긴다. 모든 필수 의무가 입증되어야 완료로 판정한다. 관찰용 지표는 자동으로 필수 집합에 편입되지 않는다. 이 결과 의미는 ADR Status나 새 저장 형식을 정의하지 않는다.

LLM 평가에는 판단할 입력과 기준 자료, 좁은 실패 규칙, 판정을 뒷받침할 근거와 판단 불가 조건이 필요하다. JSON 출력이나 낮은 생성 무작위성만으로 결정성을 주장하지 않는다. 실제 사례에서 실패 누락과 오탐을 검토하며 평가기 선택과 구체적인 프롬프트는 구현 재량이다.

#### 필수 보장

- Section 7 작성자는 Section 3과 Section 6을 먼저 읽는다.
- 모든 `7.x` Feature의 Evaluation Rubric는 전체 데모에서의 역할과 관찰 가능한 완료 결과를 연결하는 `Demo outcome` 한 줄을 포함한다.
- Demo outcome는 같은 Feature의 User Flow, 오류 처리와 Evaluation Rubric에 모순되지 않아야 한다.
- Atomic과 batch 작성 모두 기존 Feature 단위의 승인과 저장 경계를 유지한다.

#### 의도와 사전 평가 기준

| 의무                                                                                            | 관찰 가능한 검증 기준                                                                                 |
| ----------------------------------------------------------------------------------------------- | ----------------------------------------------------------------------------------------------------- |
| User Story는 대상 사용자의 문제와 얻어야 할 결과를 설명한다.                                    | 해당 Feature만 읽어도 누구의 어떤 문제가 왜 해결되어야 하는지 알 수 있다.                             |
| 각 사용자 결과에는 판정 가능한 평가 기준이 있다.                                                | 결과가 누락된 초안은 완료로 제시되지 않고, 해당 결과를 확인할 조건이 보완된다.                        |
| 각 필수 제약에는 판정 가능한 평가 기준이 있다.                                                  | 값, 단위, 권한, 금지 동작과 실패 보장을 각각 준수하거나 위반한 결과를 구분할 수 있다.                 |
| 각 평가 기준은 독립적인 의무와 용도, 적용 상황·입력, 관찰 증거, 검증 수단·판정 규칙을 특정한다. | 같은 상황의 정상 결과와 관련 반례를 서로 다르게 판정할 수 있고, 불필요한 예외를 발명하지 않는다.      |
| 필요한 증거의 종류와 통과·실패 기준은 Feature 승인 전에 제시한다.                               | 작성 완료 화면에서 어떤 결과를 test, eval 또는 demo로 확인할지 설명할 수 있다.                        |
| 품질 eval을 평가 기준으로 사용할 때는 대표 상황의 범위와 품질 판단 규칙을 정한다.               | 출력이 있다는 사실만으로 통과하지 않고, 의도에 맞는 결과와 부족한 결과를 구분한다.                    |
| 수용 여부를 바꾸는 임계값과 집계 규칙은 근거와 함께 승인받는다.                                 | 사용자가 정하지 않은 합격률을 확정 사실로 기록하지 않으며, 미정 기준에 의존하는 완료 판정을 보류한다. |
| Demo outcome는 평가 기준을 대체하지 않는다.                                                     | 전체 데모의 정상 경로가 보여도 필수 제약을 위반한 Feature는 수용되지 않는다.                          |

작성 예시도 선언한 모든 필수 값과 규칙을 수용 기준에 연결해야 한다. 한 체크박스에 독립적인 동작을 묶거나 앞에서 선언한 값을 예시의 판정 기준에서 누락하지 않는다.

초안 작성은 미정 항목을 표시하고 계속할 수 있다. 최종 Feature 승인에는 의도와 평가 기준을 함께 제시하고, 수용 여부를 바꾸는 미정 제품 결정은 기존 승인 경계에서 해결한다. 별도 의도 subsection, 평가 계획 문서나 추가 승인 단계를 만들지 않는다. 실제 사례 데이터, 테스트 코드와 실행 결과는 구현·검증 단계에서 관리한다.

#### 금지

- Section 7에 별도 `7.x.7 Feature Demo` subsection을 만들지 않는다.
- Demo outcome에 사전 조건, 전체 사용자 행동, 실패 시나리오와 성공 조건을 반복하지 않는다.
- Demo outcome에 구현 라이브러리, 코드 구조, 테스트 파일, 배포 절차, PR 또는 커밋 계획을 기록하지 않는다.

#### 실패 시 보장

- Demo outcome만으로 상세 절차가 부족하면 문서 구조를 늘리지 않고 기존 Section 3, User Flow, 오류 처리와 Evaluation Rubric를 사용해 요청 시 설명한다.

### Alternatives

1. **Section 3 전체 데모만 유지**
   - 장점: Section 7에 새 필드가 없다.
   - 단점: 개별 Feature가 전체 여정에 기여하는 지점을 빠르게 찾기 어렵다.

2. **각 Feature에 완전한 Feature Demo subsection 추가**
   - 장점: Feature 하나만 읽어도 완전한 데모 절차를 얻는다.
   - 단점: User Flow, 오류 처리와 Evaluation Rubric를 반복해 작성하고 함께 유지해야 한다.

3. **Evaluation Rubric에 Demo outcome 한 줄 추가**
   - 장점: 전체 데모와의 연결을 보존하면서 기존 Feature 명세를 반복하지 않는다.
   - 단점: 상세 데모 절차는 기존 subsection을 함께 읽거나 요청 시 파생해야 한다.

## Consequences

### Positive

- Feature를 구현하기 전에 사용자의 의도와 완료 판단의 근거를 함께 검토할 수 있다.
- Builder는 각 Feature가 전체 데모에서 담당하는 역할을 한 줄로 확인할 수 있다.
- User Flow, 오류 처리와 Evaluation Rubric가 상세 제품 행동의 단일 소스로 유지된다.
- Section 7 작성과 검토 비용이 줄고 같은 행동의 문서 간 드리프트가 사라진다.

### Negative

- 품질 판단이 필요한 Feature는 대표 상황과 수용 기준을 먼저 구체화해야 한다.
- Feature만 단독으로 읽을 때 완전한 데모 실행 절차는 보이지 않는다.
- 상세 데모가 필요하면 Section 3과 기존 Feature subsection을 함께 읽어야 한다.

### Risks

- 구현이 끝난 뒤 유리한 기준을 선택하면 원래 의도를 놓칠 수 있다. 승인된 평가 기준을 기준으로 판정하며 변경은 제품 계약 변경으로 확인한다.
- Demo outcome가 모호한 슬로건으로 퇴화할 수 있다. 역할과 관찰 가능한 완료 결과를 모두 한 문장에 포함한다.
- 상세 데모 요청이 새 영속 문서를 만들 수 있다. 설명은 기존 권위 문서에서 파생한 일시적 출력으로 유지한다.
