# ADR 0001: 파괴적 ADR rollup은 명시적 승인을 요구

Date: 2026-09-07

## Status

Proposed

## Purpose

ADR rollup은 파일을 덮어쓰고 삭제하거나 번호를 다시 매길 수 있다. renumber는 저장소 밖의 영구 링크를 끊을 수 있으므로 무응답이나 모호한 응답을 승인으로 해석하면 복구하기 어려운 변경이 발생한다.

하네스는 파괴적 범위와 결과를 보여준 뒤 명시적 승인을 받아야 하며, 승인 증거가 없으면 현재 파일과 번호를 유지해야 한다.

같은 결정의 이력이 여러 문서에 흩어져 있어도 문서 날짜나 코드의 현재 값만으로 유효한 계약을 고를 수는 없다. 일부만 대체된 문서의 나머지 계약, 미구현 제안과 적용 범위가 다른 규칙을 보존하면서 확정된 변경만 현재 본문에 모아야 한다.

기존 결정을 통합하는 작업이 매번 전체 시스템을 다시 탐색하거나 맵을 작성하는 작업으로 커져서는 안 된다. 대상 결정의 계약 보존을 판단하는 데 필요한 근거부터 읽고, 확인된 문제에 따라 조사 범위를 넓힌다.

## Decision Drivers

- 파일 삭제·덮어쓰기·경로 변경은 사용자 의도 없이 실행되면 안 된다.
- 무응답과 모호한 응답은 파괴적 변경의 승인 증거가 아니다.
- rollup은 승인된 범위만 바꾸고 나머지 category와 번호를 보존해야 한다.
- 코드에서 보이는 동작과 승인된 목표 계약을 구분하고, 해결되지 않은 충돌이 독립 결정의 준비까지 막지 않아야 한다.
- 단순한 변화 사슬은 대상과 관련 계약의 대조만으로 정리할 수 있어야 하며, 탐색과 시각화 비용이 필요한 검증 범위를 넘지 않아야 한다.

## Decision

ADR rollup은 덮어쓸 파일, 삭제할 파일과 모든 old → new 경로를 보여주고 명시적으로 승인된 파괴적 변경만 실행한다.

번호와 gap은 기본으로 유지한다. 사용자가 번호 정리를 요청하면 모든 old → new 경로와 외부 링크 영향을 제시하고 승인된 경로만 변경한다. 이미 번호 유지를 선택한 경우 같은 gap을 이유로 다시 묻지 않는다.

통합 대상은 같은 카테고리에서 같은 질문과 계약 경계의 확정된 변화 이력을 가진 결정이다. 파일의 가장 낮은 번호와 계약의 권위는 별개다. 현재 채택된 결정과 범위가 확인된 대체 관계로 본문을 구성하고, 날짜·번호·코드 값·더 엄격한 값 자체를 승자 선정 근거로 사용하지 않는다. 코드의 구현 사실은 검증 근거이며 요구사항과 채택 이유의 권위를 대체하지 않는다.

각 원문 계약은 유지, 대체, 폐기 또는 미확정으로 대조한다. 부분 대체나 여러 갈래 후속 결정이 있으면 남은 계약의 소유자를 확인하며, 소유자를 확정할 수 없는 원문은 삭제하지 않는다. 서로 다른 적용 범위의 규칙은 양립할 수 있다. 동일 조건에서 충돌하는 계약, 끊긴 대체 관계나 순환 관계는 영향받는 결정만 보류하고, 근거와 권장안·정확한 계약 변경을 하나의 결정 요청으로 제시한다. 독립 결정의 후보 준비는 계속한다.

탐색은 요청 범위의 ADR과 색인에서 시작한다. 후보 사슬의 모든 원문과 직접 관련된 계약·참조를 확인하고, 잔여 소유권이나 충돌을 해결하는 데 필요한 근거가 드러날 때만 추가 문서와 코드로 확장한다. 코드와 테스트는 통합할 계약과 구현 상태의 검증에 사용하며, 새 기능 발견이나 전체 업무·컨텍스트·이벤트 맵 작성을 기본 단계로 요구하지 않는다. 같은 실행에서 확인한 근거는 관련 내용이 바뀌지 않았다면 재사용한다.

에이전트는 필요한 근거와 검증 결과를 확보하는 범위에서 사용 가능한 탐색·읽기·비교 도구와 작업 방식을 선택한다. 특정 도구 이름이나 호출 횟수로 수행의 적합성을 판단하지 않는다. 이 재량은 승인 후 변경, 원문 삭제 전 이력 보존, 적용 직전 원문·목적지 확인과 같은 필수 순서를 바꾸지 않는다.

명확한 변화 사슬의 보고서는 계약 대조표와 변경 요약으로 충분하다. 순환, 부분 대체, 소유권 충돌이나 복잡한 참조 변경을 판단하는 데 그림이 필요한 경우에만 해당 후보 주변의 작은 전후 그래프를 제공한다. 문서 개수나 통상적인 삭제·참조 갱신만으로 그림을 요구하지 않는다. 전체 색인의 구조·참조·순환 자동 검사와 적용 직전 원문 재확인은 시각화 여부와 관계없이 유지한다.

`Proposed`는 구현 또는 완료 검토가 남았다는 뜻이며 승인 여부 자체를 확정하지 않는다. 미구현 목표를 통합하려면 그 목표가 확정된 결정인지 확인하고, 포함한 목표의 구현·검토가 남으면 통합 ADR도 `Proposed`로 유지한다. 승인되지 않았거나 채택 여부가 불명확한 제안을 현재 계약으로 자동 편입하지 않는다. 모든 현재 계약이 기존 `Accepted` 결정에서 이어지고 구현·테스트에 유지되는 경우만 완료 상태를 보존한다.

현재 본문에는 의도, 유효한 Drivers, 채택 이유와 현실적인 대안, 정확한 계약, 실패 보장과 경계, 결정에 중요한 가정과 관찰 기준을 남긴다. 주요 변화는 원래 ADR·기존 로그·확인된 Git 이력에 근거해 기록하며 이유를 만들어내지 않는다. 의미가 같은 문구와 요구사항이 아닌 구현 식별자 차이는 새로운 계약 승인 없이 후보에서 정리할 수 있다.

적용 직전에는 승인 범위의 원문과 목적지가 준비 당시와 같은지 확인한다. 바뀐 파일이나 목적지 충돌을 발견하면 해당 변경을 중단하고 기존 내용을 보존한 채 영향을 받는 후보를 갱신한다. 검증한 주요 이력을 먼저 기록하고 원문을 삭제한다. 중간 실패는 실제 적용된 범위를 명시하고 승인된 변경만 복구하며, 다른 작업을 되돌리지 않는다.

### Requirement contract

- 승인 화면은 덮어쓸 파일, 삭제할 파일과 모든 경로 변경을 표시한다.
- 승인된 category와 파일만 변경한다.
- 무응답·모호한 응답에서는 파일, 번호와 매핑을 변경하지 않는다.
- renumber를 승인하지 않으면 기존 번호와 gap을 유지한다.
- 번호 정리는 사용자 요청과 정확한 경로 승인에 한정하며, 기존 gap 유지 선택을 다시 확인하지 않는다.
- 같은 질문·소유 경계·적용 범위와 확정된 대체 관계로 통합할 계약을 선택한다. 날짜, 번호, 코드 값이나 엄격함만으로 상충하는 계약을 선택하지 않는다.
- 원문마다 남아 있는 계약의 소유자를 확인하며, 미확정 잔여 계약이 있는 파일은 삭제하지 않는다.
- `Proposed`의 승인 여부와 구현 완료 여부를 구분하고, 승인되지 않은 목표를 자동 채택하거나 미완료 목표를 `Accepted`로 표시하지 않는다.
- 계약 충돌과 불명확한 대체 관계는 해당 결정만 보류하며 독립 후보의 준비는 계속한다.
- 충돌 요청은 양쪽 근거, 적용 조건, 권장안과 이유, 정확한 계약 변경 및 이력 영향을 포함한다.
- 현재의 의도·채택 이유·유효한 Drivers·요구사항·실패 보장·경계·관찰 기준을 보존하고, 주요 전환의 이유는 원문 근거가 있을 때만 기록한다.
- 적용 직전 원문 변경이나 목적지 충돌이 있으면 영향받는 변경을 중단하며, 승인 범위 밖의 파일과 동시 작업을 덮어쓰지 않는다.
- 원문 삭제 전에 검증된 주요 이력을 기록하며 적용 실패의 실제 부분 상태를 보고한다.
- 통합 탐색은 요청 범위의 ADR·색인과 후보의 모든 원문 및 직접 관련 계약에서 시작하며, 확인된 잔여 소유권·충돌·참조 문제를 해결할 때만 확장한다.
- 새 기능 발견이나 전체 업무·컨텍스트·이벤트 맵을 rollup의 기본 단계나 완료 조건으로 요구하지 않는다.
- 코드·테스트 조사는 통합할 계약과 구현 상태의 검증에 필요한 범위로 한정하고, 같은 실행의 변경 없는 근거를 재사용한다.
- 단순한 변화 사슬은 계약 대조표와 변경 요약으로 설명하고, 판단에 필요한 경우에만 후보 주변의 작은 전후 그래프를 제공한다. 문서 개수나 통상적인 삭제·참조 갱신만으로 그림을 강제하지 않는다.
- 탐색과 그림을 줄여도 전체 색인의 구조·참조·순환 자동 검사, 잔여 계약 확인, 승인 범위와 적용 직전 원문 재확인을 생략하지 않는다.
- 필요한 근거·검증 결과와 승인·보존 순서를 지키는 한 도구와 작업 방식은 에이전트가 선택한다. 특정 탐색 도구·호출 순서·횟수를 같은 결과를 내는 다른 방식의 거절 근거로 삼지 않는다.

### 관찰 가능한 검증 기준

- 같은 계약을 표현만 바꾼 원문은 의미를 보존하며 통합하고, 범위가 다른 규칙은 모순으로 오인하지 않는다.
- 최신 미승인 제안, 서로 충돌하는 유효 계약, 부분 대체 후 남은 계약이 있는 입력은 해당 계약과 원문을 보존한다.
- 번호 유지나 일부 범위 승인은 그 범위만 적용되며 추가 선택 없이 다른 번호나 카테고리가 바뀌지 않는다.
- 승인 대기 중 원문이나 목적지가 바뀐 입력과 중간 적용 실패에서도 원래 계약과 다른 작업이 보존된다.
- 범위가 지정된 명확한 변화 사슬은 관계없는 기능의 상세 탐색이나 전체 맵 없이 검토되며, 세 개 이상의 ADR이라는 이유만으로 그림이 추가되지 않는다.
- 직접 관련 계약에 잔여 소유권 문제가 있으면 그 근거를 따라 조사를 확장하고, 단순히 탐색을 줄이기 위해 미확정 원문을 삭제하거나 검증 통과로 표시하지 않는다.
- 서로 다른 도구나 읽기 묶음을 사용해도 같은 원문 근거와 현재성·검증 결과를 확보하면 허용하며, 도구 사용 선언만 있고 근거나 결과가 없으면 통과시키지 않는다.

### Alternatives

1. **무응답 시 gap 자동 정리**
   - 장점: 번호가 연속적이다.
   - 단점: 외부 링크를 끊는 rename을 승인 없이 실행한다.
2. **모든 gap 유지**
   - 장점: 경로가 안정적이다.
   - 단점: 사용자가 명시적으로 요청한 번호 정리도 할 수 없다.
3. **명시 승인된 renumber만 실행**
   - 장점: 경로 안정성과 정리 선택권을 함께 보존한다.
   - 단점: 파괴적 변경 전에 승인 단계가 필요하다.

## Consequences

### Positive

- 무응답이 파괴적 변경으로 이어지지 않는다.
- 사용자는 삭제와 경로 변경 범위를 승인 전에 확인한다.

### Negative

- 번호 gap을 제거하려면 명시적 선택이 필요하다.
- 충돌한 결정이나 변경된 원문은 재검토가 끝나기 전까지 통합할 수 없다.

### Risks

- 승인 화면이 경로 변경을 누락할 수 있다. deterministic plan과 최종 lint가 표시 대상과 실제 변경을 대조해야 한다.
- 대상 중심 탐색을 고정된 한 단계 참조 제한으로 오해하면 잔여 계약을 놓칠 수 있다. 필요한 소유권 근거와 참조를 끝까지 확인하고 미확정 상태를 그대로 보고한다.
