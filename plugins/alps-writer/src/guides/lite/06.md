<section_guide number="6" title="Success Criteria" references="1,2,3,4,5">
<purpose>Separate release acceptance from outcome observation, and define KPIs with their tension metrics.</purpose>

<questions>
1. Ask only for a baseline, target, or required use the user has not supplied and that cannot be proposed as a candidate.
</questions>

<workflow>
Read Sections 1-5. State release acceptance: every Required BR, FR, NFR, and EC must pass. KPIs and
tension metrics observe the outcome after release and gate release only when the user confirms
them as required with a basis.

Propose KPIs from the intent and any signal the user supplied. Define each as `KPI-n` with its
purpose, business calculation (population, numerator, denominator, unit, direction, observation
window), baseline and target only when supplied or approved, related BR and FR IDs, and required
or monitoring use. Users rarely think of tension metrics, so for every KPI always propose one:
name the abuse or opposite-failure scenario that raises the KPI while defeating the purpose and the
same-purpose measure that worsens in it, or an observable counterexample when a number is
unsuitable. When a Required item already catches the shortcut, name it as the guard instead.

Record the decision for every KPI: an adopted `TM-n` in its own table row (calculation, protected
KPI, scenario, use), the guarding Required IDs, or not adopted. A declined candidate never blocks
completion. Do not add sample design, data collection, or instrumentation; Full ALPS adds them.
When no KPI applies, record that after the release-acceptance statement.
</workflow>

<completion required="true">Confirm release acceptance, every KPI, and every tension decision before saving 6.1.</completion>
</section_guide>
