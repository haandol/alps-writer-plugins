# 주문·결제 예제로 배우는 Ontology Writer

## 목표

하나의 업무 자료가 이벤트 스토밍 보드, 저장 온톨로지, ADR(아키텍처 결정 기록)의 계약과 테스트로 어떻게 이어지는지 따라간다. 보드의 상태 변화와 저장 모델의 관계, 형식 검증과 실제 실행 검증을 구별할 수 있게 한다.

## 배경

이 예제는 가상의 상점에서 고객의 주문을 접수하고 결제 결과를 받아 주문을 확정하는 업무다. 입력 자료와 보드·모델은 설명을 위해 작성했으며 실제 프로젝트의 정책, 사용자 승인 기록이나 업무 실행 결과가 아니다. 전체 절차는 [온톨로지 생성·활용 가이드](./workflow.md)에서 설명한다.

> 이 예제의 정상 흐름은 주문 접수, 결제 요청, 외부 제공자의 대금 결제, 주문 확정이다. 명시한 상태 변화는 후보 보드에 표시하고, 저장 모델에는 사건·정책·업무 관계를 남긴다. 실제 구현에 필요한 상태와 조건은 ADR 계약으로 확정한다.

<a id="business"></a>

## 1. 어떤 업무를 설명하는 예제인가

주문 관리와 결제 처리가 사건을 주고받아 주문을 확정한다. 주문 관리는 구매 요청과 확정 결과를, 결제 처리는 결제 요청과 수납 결과를 책임진다. 이 구분은 예제의 업무 책임이며 서비스 배포 단위를 정한 것은 아니다.

### 입력 자료와 결과 파일

| 파일                                                                                                                                         | 읽을 내용                                                                  |
| -------------------------------------------------------------------------------------------------------------------------------------------- | -------------------------------------------------------------------------- |
| [업무 자료](../examples/order-payment/business-notes.md)                                                                                     | 수행자, 정상 흐름, 전후 상태, 반응 정책과 아직 정하지 않은 질문            |
| [후보 보드 JSON](../examples/order-payment/board.json)                                                                                       | 자료의 어느 부분에서 사건·상태 변화·정책·질문을 가져왔는지와 출처 판정     |
| [저장 모델](../examples/order-payment/docs/ontology/order-payment.ttl) · [예제용 ADR 색인](../examples/order-payment/docs/adr/.mapping.json) | 같은 흐름을 표현한 Turtle 관계와, 아직 실현 기능을 등록하지 않은 시작 상태 |

모델과 빈 색인은 플러그인 안의 예제 폴더에 있다. 아래 읽기·검증 명령은 `--adr-dir`로 이 예제만 지정한다. 실제 프로젝트의 모델이나 색인을 이 파일들로 덮어쓰는 절차가 아니다.

### 사건과 수행자를 따라 읽기

| 수행자와 행동                | 자료에 명시한 변화             | 보드에서 읽는 사건과 계기                                      |
| ---------------------------- | ------------------------------ | -------------------------------------------------------------- |
| 고객이 주문 접수             | 주문이 없음 → 결제 대기        | 주문 접수됨. 해당 주문에 결제가 없으면 결제 요청을 시작        |
| 고객이 결제 요청             | 결제 요청이 없음 → 결제 요청됨 | 별도의 발생 사건은 미기록. 다음 대금 결제와는 진행 순서로 연결 |
| 외부 제공자가 대금 결제      | 결제 요청됨 → 결제 완료        | 결제 완료됨. 해당 주문의 결제일 때 주문 확정을 시작            |
| 주문 처리 시스템이 주문 확정 | 결제 대기 → 주문 확정          | 주문 확정됨                                                    |

주문과 결제 내역은 식별자가 있는 업무 대상이라는 자료의 가정에 따라 보드에서 엔티티로 표현한다. 애그리거트가 보장해야 할 일관성 경계까지 확인한 것은 아니므로 애그리거트로 분류하지 않았다.

### 정하지 않은 경로도 함께 읽기

결제 실패 시 주문 처리, 결제 거절 후 재시도 주체·방식, 결제 완료 사건의 중복 수신 처리는 질문으로 남아 있다. 이 질문들은 자료에서 빠진 부분을 보완하기 위한 출발점이다. 보드가 정상 흐름을 보여준다는 이유로 자동 취소나 중복 처리 정책을 채우지 않는다.

후보 보드의 `stated`는 학습용 자료가 직접 명시했다는 뜻이다. 실제 업무에서 확인되었다거나 사용자가 모델 저장을 승인했다는 뜻은 아니다. 이 예제는 주문 운영을 핵심 업무, 대금 결제를 지원 업무로 가정하고 그 소속을 자료에 명시했다. 실제 프로젝트의 분류는 해당 업무의 근거로 판단해야 한다.

<a id="representations"></a>

## 2. 보드와 저장 모델을 나란히 읽기

두 표현은 같은 업무를 다루지만 보존하는 내용이 다르다. 보드는 자료에 명시한 전후 상태와 출처까지 보여주고, 저장 모델은 정해진 어휘로 업무 관계를 표현한다.

### 후보 보드 열기

이 저장소의 루트에서 다음 명령을 실행한다. 설치된 플러그인을 사용할 때는 프로젝트 폴더를 작업 위치로 두고, `plugins/ontology-writer` 부분을 실제 플러그인 설치 경로로 바꾼다. Node.js 24 이상이 필요하다.

```bash
node plugins/ontology-writer/scripts/eventstorming-view.mjs \
  plugins/ontology-writer/examples/order-payment/board.json --lang ko
```

명령은 일회성 HTML을 만들고 기본 브라우저로 연다. 화면을 열지 않고 경로만 확인하려면 `--no-open`을 붙인다. 모델이 없어도 후보 보드는 열 수 있으며 모델·ADR·색인은 변경하지 않는다.

각 묶음은 위에서 아래로 **주체·행동 → 확인된 변화 → 발생 사건**을 읽는다. 고객은 주문서를 참고해 주문을 접수하고,
결제 선택 화면을 참고해 결제를 요청한다. 주문 확정의 결과 뷰는 주문 현황이다. 뷰는 화면이나 조회 모델의 역할을 뜻한다.
외부 결제 제공자나 주문 처리 시스템의 행동에 사람의 화면 조작을 덧붙이지 않으며, 자료에 없는 뷰는 미기록으로 표시한다.

주 연결선을 따라 주문 접수됨에서 중간 행동인 결제 요청, 결제 완료됨, 주문 확정됨까지 읽는다. 결제 요청은 발생 사건이 미기록인 행동이므로 별도의 도메인 이벤트로 바꾸지 않았다. 선의 “반응”·“순서” 표시를 선택하면 원래의 정책·행동·조건과 근거를 확인한다.

**전체 업무 영역**을 선택하면 온라인 상점 도메인 안에서 주문 운영·대금 결제 서브도메인과 각각의 컨텍스트를 본다.
컨텍스트를 선택하면 소속·활동·근거가 열리고, 그 안의 사건을 선택하면 개별 사건 흐름으로 돌아간다. 컨텍스트 사이의
화살표는 기록된 인계다. 서브도메인과 컨텍스트를 언제나 일대일로 배치하는 규칙은 아니며, 복수 소속이면 같은 컨텍스트를
한 번만 표시하고 소속 이름을 나열한다.

주문 확정됨 사건을 선택하면 연결된 상류·하류 경로가 강조된다. 수행 주체인 주문 처리 시스템, 업무 대상인 주문, 결제 대기에서 주문 확정으로의 변화, 입력 사건과 반응 조건도 읽을 수 있다. 근거를 펼치면 [업무 자료의 정상 흐름](../examples/order-payment/business-notes.md#normal-flow)과 [정책](../examples/order-payment/business-notes.md#policies)을 가리키는 출처를 확인한다.

캔버스는 드래그로 이동하고 휠이나 확대 버튼으로 살펴본다. 흐름 신호는 실제 통신이 아닌 관계의 방향 설명이다.
효과가 정지했다면 캔버스 아래 상태 문구에서 사용자 정지·기기의 모션 감소 설정·화면 숨김 등을 구별할 수 있다.

### 저장 모델 검증·조회·보기

다음 명령들도 저장소 루트에서 실행한다. `--adr-dir` 옆의 `ontology/`에 있는 예제 모델을 읽는다.

```bash
node plugins/ontology-writer/scripts/ontology.mjs validate \
  --adr-dir plugins/ontology-writer/examples/order-payment/docs/adr

node plugins/ontology-writer/scripts/ontology.mjs query \
  --process ordering.place-order \
  --adr-dir plugins/ontology-writer/examples/order-payment/docs/adr

node plugins/ontology-writer/scripts/ontology.mjs view \
  --adr-dir plugins/ontology-writer/examples/order-payment/docs/adr --lang ko
```

검증은 요소·관계·필수 속성과 연결의 형식을 확인한다. 조회는 주문 프로세스와 연결된 결제 사건·정책·규칙·미정 범위를 돌려준다. 보기는 사건 흐름과 3D 업무 구조를 제공하지만 업무를 실행하거나 Status를 바꾸지는 않는다.

저장 모델의 결제 완료와 주문 확정 연결은 다음과 같다. 아래는 전체 모델에서 관계 부분만 발췌한 것이다.

```turtle
m:payment.payment-completed
    onto:triggers m:ordering.confirm-on-payment .

m:ordering.confirm-on-payment
    onto:reactionCondition "완료된 결제가 확정하려는 주문의 결제이다." ;
    onto:starts m:ordering.confirm-order .
```

`triggers`는 사건이 정책을 촉발한다는 관계이고, `starts`는 조건이 맞을 때 정책이 시작하는 단계를 가리킨다. `flowsTo`로 기록한 진행 순서가 이 조건을 대신하지 않는다.

### 저장 모델 보기에서 상태가 미확인인 이유

후보 보드에는 업무 자료의 전후 상태가 있다. 저장 모델에는 `Step`, `BusinessEvent`, `Policy`, `BusinessConcept` 등 정해진 업무 요소를 사용하며, 엔티티의 `before`·`after`나 상태 기계를 추가하지 않았다.

따라서 저장 모델 보기에서 주문의 변화가 미확인으로 나오는 것은 그 모델에 기록된 관계만 사용했기 때문이다. `uses 주문`을 보고 결제 대기에서 확정으로 바뀌었다고 추론하지 않는다. 상태와 전이를 구현에 사용할 때는 자료를 근거로 ADR의 계약에 보존해야 한다.

저장 어휘에는 도메인·서브도메인·뷰 요소도 없다. 저장 모델의 영역 보기에서는 두 컨텍스트를 찾을 수 있지만,
서브도메인 소속·분류와 뷰는 미확인이다. 이 예제의 풍부한 영역·뷰 표현은 업무 자료를 함께 반영한 후보 보드에서 확인한다.

## 3. 어떤 내용을 ADR과 테스트에 연결하는가

업무 모델을 채택해 실제 기능을 개발한다면, 내부 시스템 단계마다 실현 기능과 ADR 계약이 필요하다. 이 예제에는 기능이나 ADR 구현을 넣지 않았으므로, 다음 내용은 계약으로 넘길 항목을 설명하는 초안이다.

### 실현 기능 연결과 계약 후보

| 기능 카테고리의 예 | 연결할 모델 단계          | ADR에서 구체화할 내용                                                                   |
| ------------------ | ------------------------- | --------------------------------------------------------------------------------------- |
| `ordering/submit`  | `ordering.submit-order`   | 어떤 구매 요청을 받아 주문을 만들고 결제 대기 상태와 주문 접수 사건을 보장하는가        |
| `payment/request`  | `payment.request-payment` | 결제 요청을 시작할 조건, 요청되는 대금과 주문의 관계, 외부 제공자에 의존하는 범위       |
| `ordering/confirm` | `ordering.confirm-order`  | 해당 주문의 결제 완료인지 확인하는 조건, 결제 대기에서 주문 확정으로의 전이와 발생 사건 |

이 표는 기능 구분의 예다. 하나의 기능이 여러 단계를 실현할 수 있고, 해당 결정을 이미 다루는 ADR이 있으면 재사용한다. 단계 수에 맞춰 ADR 문서를 늘리는 방식은 아니다.

실제 연결은 해당 카테고리의 `realizes`에 기록한다. 예를 들어 주문 확정 기능은 `ordering.confirm-order`를 실현한다. 연결을 적는 것과 계약을 구현·검증하는 것은 별개의 작업이다. 예제의 빈 `categories`는 아직 아무 기능도 등록하지 않았다는 뜻이며, 확인된 무관 기능을 나타내는 `realizes: []`와도 다르다.

수납 금액이 주문 금액과 같아야 한다는 규칙은 관련 기능의 준수 계약에 반영해야 한다. 어떤 입력을 확인하고 무엇을 거절할지, 외부 결제 결과를 어떤 조건에서 수용할지 ADR에서 정한다. 외부 제공자의 내부 구현을 이 프로젝트의 실현 기능으로 만들어 넣지는 않는다.

### 정상·반례·미정 사례

아래는 위 계약을 승인한 뒤 테스트로 구체화할 사례다. 예제의 주문 A와 B는 서로 다른 주문을 뜻하는 임의의 식별자다.

| 상황과 입력                                                             | 관찰할 내용                                                                       |
| ----------------------------------------------------------------------- | --------------------------------------------------------------------------------- |
| 결제 대기 중인 주문 A에 대해 조건과 금액 규칙을 충족한 결제 완료를 받음 | 주문 A가 확정되고 그 주문의 확정 사건을 확인                                      |
| 주문 A를 확정하려는데 결제 완료가 주문 B의 것임                         | A의 확정 조건이 충족된 것으로 처리하지 않음. 상세한 거절·응답 계약은 ADR에서 확인 |
| 수납 금액이 주문 금액과 다름                                            | 금액 일치 규칙을 충족한 성공으로 판정하지 않음. 처리·오류 계약을 먼저 구체화      |
| 이미 처리한 결제 완료를 다시 받음                                       | 자료에 응답 정책이 없으므로 기대 결과를 임의로 정하지 않고 추가 확인              |

실제 테스트는 승인된 ADR의 입력·관찰 결과·판정 기준을 따라야 한다. 이 표만으로 테스트 파일이 생기거나 구현 완료가 판정되지는 않는다.

### 추가 자료가 생겼을 때

예를 들어 결제 거절 후 재결제를 시작하는 주체와 조건을 추가로 확인했다면, 그 자료로 `/ontology-build`에 기존 모델과의 비교를 요청한다. 업무 정책을 바꾸려면 `/ontology-edit`로 의미 차이와 영향받는 ADR 개정을 함께 준비한다.

이때 이미 확인한 정상 흐름 전체를 새로 만들거나, 새 자료에 나오지 않은 기존 경로를 삭제하지 않는다. 추가된 사실과 필요한 계약 변경을 확인한 뒤 반영한다. 재시도 횟수·대기 시간처럼 아직 제공하지 않은 값은 계속 미정으로 남긴다.

<a id="readiness"></a>

## 4. 이 예제는 어디까지 준비된 상태인가

모델의 구조를 검증하고 화면을 열 수 있지만, 실제 주문·결제 기능을 구현하거나 실행한 예제는 아니다. 두 프로세스는 `Proposed`이고, ADR 색인은 비어 있다.

### 세 가지 판정으로 읽기

| 판정               | 이 예제에서 확인할 수 있는 범위                                                                                   |
| ------------------ | ----------------------------------------------------------------------------------------------------------------- |
| 업무 모델의 충분성 | 정상 흐름·수행자·반응 정책과 금액 규칙은 자료에 있다. 실패·재시도·중복 수신은 추가 확인이 필요한 범위로 남아 있음 |
| ADR 계약의 준비    | 기능 연결과 실제 ADR이 아직 없으므로 계약 작성·확인이 필요함                                                      |
| 실제 실행 검증     | 주문 접수·결제 요청·주문 확정 기능을 실행하지 않았으므로 미검증                                                   |

구조 검증 통과를 세 판정의 통과로 합치지 않는다. 특히 보드에서 자료가 명시한 상태를 보여주는 것과 실제 코드에서 상태 전이를 관찰한 것은 다르다.

### 정렬 계획으로 누락 확인하기

주문 프로세스의 계획을 확인하면서, 결제 프로세스도 함께 검토할 실행 범위에 포함하려면 다음과 같이 지정한다.

```bash
node plugins/ontology-writer/scripts/ontology.mjs align \
  --process ordering.place-order --together payment.take-payment \
  --adr-dir plugins/ontology-writer/examples/order-payment/docs/adr --json
```

이 명령은 실제 결제를 실행하지 않고 선택한 프로세스의 선행 조건과 검토 범위를 계산한다. `--together`를 지정했다고 상대 프로세스의 모든 선행 검사가 이 명령 하나로 끝나는 것은 아니다. 두 프로세스를 모두 판정하려면 각각의 계획과 실행 근거를 확인한다. 예제에는 실현 기능이 없어 준비되지 않은 조건을 보고하며 종료 코드 `1`을 반환하는 것이 예상 결과다. 화면·모델 생성 실패를 뜻하지 않는다.

실제 기능과 ADR을 연결한 뒤에는 스킬 `/ontology-align`이 그 기능의 진입점을 실행하고 관찰 기준을 확인해야 한다. 검토 조건과 실행 근거를 갖추기 전에는 예제의 Status를 `Accepted`로 바꾸어 완료를 표시하지 않는다.
